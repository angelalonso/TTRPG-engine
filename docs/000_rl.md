# Playtesting and learning faster routes

The playtester is a **local command-line planning tool**, not a desktop UI
button or a guarantee of the optimal route. It can let you play a simulated
game manually, compare against random actions, train an automatic player, and
explain its route and rewards. It does not modify your saved games.

## Start here: play, then teach

Run from the repository root:

```sh
make playtest-prepare
make playtest-manual RL_GOAL="charisma>=10" RL_MAX_DAYS=365 \
  RL_OUTPUT=rl/data/manual.json
```

Manual mode shows your characteristics, inventory, quests, pending events,
and legal actions. Enter an **action ID**, `/work` to filter choices, `?` to
reset the filter, or `q` to stop and export the partial route. Each action
shows its reward components. It is useful for checking that a goal is possible
before spending hours training. It does not train PPO from your choices.

Next measure an untrained baseline using the same goal and limits:

```sh
make playtest-random RL_GOAL="charisma>=10" RL_MAX_DAYS=365 \
  RL_EPISODES=20 RL_OUTPUT=rl/data/random-baseline.json
make playtest-report RL_OUTPUT=rl/data/random-baseline.json
```

Train a first experiment, evaluate on separate seeds, then inspect its route:

```sh
make playtest-train RL_GOAL="charisma>=10" RL_MAX_DAYS=365 \
  RL_TIMESTEPS=100000 RL_PROGRESS=1 RL_MODEL=rl/models/first
make playtest-evaluate RL_GOAL="charisma>=10" RL_MAX_DAYS=365 \
  RL_MODEL=rl/models/first RL_OUTPUT=rl/data/evaluation.json
make playtest RL_GOAL="charisma>=10" RL_MAX_DAYS=365 \
  RL_MODEL=rl/models/first RL_EPISODES=1 RL_TRACE=decisions \
  RL_OUTPUT=rl/data/route.json
make playtest-report RL_OUTPUT=rl/data/route.json
```

These are starting experiments, not a promise that 100,000 steps suffices.
Keep the goal, limits and reward settings consistent across commands. Make's
default goal is `championships:level=1,count=1`; the direct Python scripts'
historical default is `charisma>=100`. Specify a goal explicitly to avoid
accidentally comparing different tasks.

## What reinforcement learning is doing

An **action** is one choice: work, buy equipment, enter an event, wait, etc.
An **episode** is one new game until success, death, a limit, or manual stop.
A **timestep** is one chosen action, not necessarily one game day.
A **policy** is the learned action selector; PPO is the learning algorithm.
A **reward** is a teaching score, not money or evidence of winning.
An **action mask** excludes choices the engine currently considers illegal.
A **seed** makes the simulated randomness repeatable.

Training tries many episodes and adjusts a policy toward higher discounted
reward. Evaluation freezes the policy and measures it on other seeds.
The Rust engine owns transitions and legality; Python does not bypass costs.
An invalid action is reported, not silently replaced with waiting.

For "reach the goal as fast as possible", use this order:

1. Establish that a route exists manually and get some trained successes.
2. Compare **success rate first**, then successful-run days and steps.
3. Add a modest time cost, rerun the same evaluation seeds, and check that
   faster winning runs did not come at the price of many more failures.
4. Inspect several successful and failed routes, not just the best seed.

Do not optimize the mean duration of *all* runs: dying immediately looks
very fast! Reports retain that statistic but separately show
`successful_mean_days`, `successful_median_days`, `successful_p90_days`,
`fastest_success_days`, and `fastest_success_seed`. Successful timing is `null`
when there are no wins. P90 is an empirical estimate and is unstable with
few wins. Use at least 20 episodes initially, then 100 or more for promising
strategies. A small difference in success rate may just be random variation.

To replay a candidate route, set `RL_SEED` to its fastest successful seed,
use one episode and the same model/configuration. That is one reproducible
example, not proof of a globally fastest route.

## Goals and run limits

| Setting | Meaning |
|---|---|
| `RL_GOAL="charisma>=10"` | Reach a positive target for a characteristic ID |
| `RL_GOAL="championship:honda_civic_fm_national"` | Obtain a particular championship trophy |
| `RL_GOAL="championships:level=1,count=1"` | Obtain a number of trophies of one level |
| `RL_MAX_DAYS=365` | Stop after this many elapsed game days |
| `RL_MAX_STEPS=2000` | Stop after this many actions, including zero-day choices |
| `RL_STAGNATION_WINDOW=100` | Warn about long stretches without better goal progress |

Malformed goals, unknown characteristic/championship IDs, non-positive limits,
and initially completed goals are rejected rather than silently defaulted.
Trophy-count goals still require you to verify that enough trophies of the
requested level actually exist and are reachable. Use stable CSV IDs, not
display names.

`goal_reached`, `dead`, `dead_money`, and `dead_stamina` are terminal outcomes.
`max_days` and `max_steps` are **time limits**, not evidence that the goal is
unreachable. `user_stopped` is an incomplete manual experiment.
The engine will not award repeated terminal rewards after an episode ends.

Choose limits large enough for required calendar events, but not an arbitrary
20-year horizon when the intended solution takes a few months. Steps and days
need separate limits because buying/selling may not advance the calendar.

## Set rewards and penalties

Copy `rl/rewards.example.json` to a separate experiment file, edit it, then
pass `RL_REWARD_CONFIG=path/to/rewards.json` to training, evaluation, manual
play, random play, or collection. Direct Python and the Rust binary accept
`--reward-config path/to/rewards.json`.

The example is an **opt-in experiment**, not a change to existing defaults.
It uses gentler safety penalties and a small per-action cost. Omit fields to
keep engine defaults; unknown field names and wrongly signed penalties are
rejected. JSON must contain finite numbers.

| Field | Engine default | When applied |
|---|---:|---|
| `goal` | 1000 | Once when the goal is reached |
| `death` | -1000 | Once on terminal death/resource failure |
| `day` | -1 | Multiplied by elapsed game days |
| `step` | 0 | Every action, even if no day passes |
| `invalid_action` | -10 | When an attempted choice is illegal or fails |
| `progress_scale` | 5 | Multiplied by the change in normalized goal progress |
| `low_stamina_threshold` | 10 | Safety threshold for the `stamina` characteristic |
| `low_stamina_penalty` | -10 | Each action at or below that threshold |
| `low_budget_threshold` | 950 | Safety threshold for the `budget` characteristic |
| `low_budget_penalty` | -10 | Each action below that threshold after the grace period |
| `low_budget_start_day` | 30 | First absolute game day with the budget penalty |

Safety penalties are specific to datasets with `budget` and `stamina`; absent
characteristics are not penalized. They measure the resulting state, not a
new threshold crossing, so repeated actions can accumulate a large cost.
Zero disables a penalty or progress shaping.

Every path action records `reward_components`; the readable report also
shows component totals and engine errors. Sum the components to understand
the score. Before increasing a penalty, inspect how often it fires.

**Common reward traps:**

- A huge low-budget penalty can teach the agent never to buy the equipment
  required to win. Lower it or its threshold, or lengthen the grace period.
- Penalizing low stamina too aggressively can make necessary recovery appear
  expensive. Inspect the days spent recovering and the total safety cost.
- A day penalty alone does not discourage zero-day loops. Try `step: -0.05`
  and compare winning routes; do not penalize all necessary purchases heavily.
- Strong negative rewards can make dying sooner preferable to continuing.
  For example, a win after 7,300 days already costs 7,300 with `day: -1`,
  before safety costs, against a bonus of only 1,000. Shorten a justified
  horizon or reduce time/safety costs before blindly increasing death costs.
- Normalized characteristic progress is bounded between 0 and 1. Trophy
  progress normally appears only when trophies are awarded, **not** after
  every prerequisite purchase or race. Increasing `progress_scale` cannot
  invent missing intermediate feedback.
- Do not reward raw money, inventory count or repeated activity merely because
  they seem useful: the agent may farm them forever instead of completing the
  real objective. Progress shaping can also be gamed through reversible
  changes under discounting. Check for cycles and compare `progress_scale: 0`.

Change one thing per experiment and use a new model/output name. A reward is
a preference, not a hard safety constraint. Critical constraints belong in
game rules/action legality; do not assume a large penalty makes something
impossible.

## Troubleshooting: symptom to next action

| Symptom | What to check and do |
|---|---|
| No wins at all | Try the goal manually. Inspect random and failed traces, prerequisites, calendar availability and terminal conditions. Start with an attainable characteristic milestone before a full championship. Then increase training budget if progress is real. |
| Long "no progress" warning | Look for waits, recovery, saving for required equipment, or repeated buy/sell choices. Sparse trophy progress can be normal. The warning never auto-kills a run. |
| Only waiting, or one repeated action | Compare `RL_STOCHASTIC=1` with deterministic play. Try `RL_ENT_COEF=0.01`, a small step cost, or a simpler goal. Inspect legal alternatives before deciding exploration is the problem. |
| Money/stamina death | Inspect the final actions, recurring costs, commitments and recovery. Try a small relevant safety penalty. Check that a viable safe route actually exists. |
| Hits max days | Check whether the next required event is outside the horizon. Increase days only when justified; otherwise inspect wasted waits and a goal the policy never learned. |
| Hits max steps while days barely move | Inspect zero-day actions and pending encounters/events. Try a small step penalty. Increasing days cannot fix a zero-day loop. |
| Reward increases but wins do not | Suspect reward hacking. Read component totals and successful timing. Reduce shaping, remove exploitable auxiliary rewards, and inspect the path. |
| Starts well, becomes worse | Evaluate earlier `-step-N.zip` checkpoints on identical seeds. Keep the most reliable/fastest winning checkpoint, not automatically the final one. |
| Good training, poor evaluation | Suspect overfitting or chance. Try multiple training seeds, more independent evaluation episodes, and compare the same task/settings. Do not tune on final-test seeds repeatedly. |
| Distant goals are ignored | `gamma=0.99` discounts a reward 1,000 actions away to about 0.000043 of its value. Try `RL_GAMMA=0.999` (about 0.368), a shorter meaningful goal, and longer rollouts. Gamma counts actions, not days. |
| Training seems frozen | Enable `RL_PROGRESS=1`. An episode may last thousands of actions; zero completed episodes is not automatically a hang. Check throughput and reduce trace logging. The large action catalogue and CPU PPO can be expensive. |
| Illegal-action error despite a mask | Treat this as an engine/mask bug or unexpected failed transition. Keep the seed, dataset, action key and error; reproduce manually before adjusting penalties. |
| Model mismatch error | Restore its original dataset/goal, or retrain. Renamed/reordered actions can silently corrupt old policies even when shapes match; metadata blocks this. |
| Legacy-model warning | Old models have no verifiable metadata. They remain loadable, but retraining is the safe choice after dataset/action changes. |
| Different routes on the same seed | Keep model, dataset, reward file, limits, dependencies and deterministic/stochastic mode identical. Stochastic sampling is reseeded per episode, but cross-platform/library bitwise reproducibility is not guaranteed. |
| Every reported run ends immediately | Check whether the target is already met, initial resources are terminal, or limits are invalid. Fix the task rather than training an empty episode. |
| Policy seems unable to distinguish situations | The current policy sees numeric characteristics, day/counts and legality, not every identity/history detail. Different game states can look identical to it. Inspect structured traces; additional versioned observations or a recurrent policy may be needed. |
| "Fastest route" requires impossible race wins | Event-result actions currently submit outcomes/positions. This is a planning assumption, not an external racing skill model. Validate the route with real game results. |

An RL run cannot prove an unreachable goal. To investigate a suspected true
dead end, save its trace, identify the **last viable state**, list missing
requirements, and check whether any legal action can restore them. Repeat
with another seed and manual choices. If the same prerequisite is impossible
even manually, investigate game data/rules rather than punishing the learner.
There is no general reachability solver in this tool.

## Checkpoints, continuation and fair comparisons

Training saves every `RL_CHECKPOINT_INTERVAL=10000` actions, plus the final
model. Ctrl+C/SIGTERM attempts to save `<model>-interrupted.zip`; abrupt
process termination/power loss cannot run that handler, so keep periodic
checkpoints. A mid-rollout checkpoint may precede the next PPO update.

```sh
make playtest-train RL_GOAL="charisma>=10" RL_MAX_DAYS=365 \
  RL_MODEL=rl/models/continued RL_RESUME=rl/models/first-step-10000.zip \
  RL_TIMESTEPS=100000 RL_GAMMA=0.999 RL_ENT_COEF=0.01
```

Resume means additional learning from saved policy/optimizer state, **not**
an exact continuation of the engine episode or RNG stream. Explicit training
arguments apply on resume; defaults are not inherited from your old command.
Keep the original settings unless intentionally running a new experiment.
For a changed goal, train a new model rather than removing the metadata guard.

Each new model has a `.zip.json` sidecar recording environment settings,
reward overrides, timesteps, and a contract with goal, action order,
characteristic order, observation version and a dataset CSV/Python hash.
Training hyperparameters are recorded for comparison too.
Keep it beside the model. Changed rewards/limits are allowed for intentional
experiments, so you must still make comparisons on identical settings.

Make uses training seed 1 (`RL_TRAIN_SEED`), evaluation seed 10000
(`RL_EVAL_SEED`), and final playtest seed 20000 (`RL_SEED`), incremented once
per episode. Keep evaluation and final ranges outside the training episode
seed range. Compare changes on the same evaluation seeds, and reserve final
seeds for a final check. Repeat promising experiments with several training
seeds. One lucky training run is not a reliable improvement.
Automatic training resets advance the seed instead of replaying exactly the
same new game every episode; an explicit reset seed restarts that sequence.

## Traces and learning from the route

`RL_TRACE=actions` is compact. `observations` includes structured state before
and after each choice. `decisions` additionally ranks legal policy choices.
Decision probabilities indicate preference, **not** probability of winning,
certainty, or a natural-language explanation of the policy's reasoning.
Detailed traces can be large; use a few episodes for diagnosis, many compact
episodes for measurement.

```sh
python3 rl/translate_playtest.py rl/data/route.json --episode 0
python3 rl/translate_playtest.py rl/data/route.json \
  --episode 0 --output rl/data/readable.txt
```

Read a successful route as a proposed walkthrough: which resources to secure,
what to buy, which prerequisites to meet, when to recover, and which calendar
events to enter. Compare it against a failed seed and test the strategy
yourself. You cannot load this trace as a desktop save or automatically replay
it into a live game.

`make playtest-collect RL_GOAL="charisma>=10"` writes masked random JSONL
trajectories to `rl/data/random.jsonl`. It honors the same reward/limit/seed
settings and is also readable by the formatter. Collection/manual traces are
for debugging or future imitation work, not automatically training examples
for the current PPO trainer.

## Direct Python, optional dependencies and engine protocol

`make playtest-prepare` creates `.venv`, installs `rl/requirements.txt`, and
builds `src-tauri/target/release/rl_env`. Python/ML dependencies are optional
for the normal desktop application and Rust engine. Manual/random play needs
Gymnasium and NumPy but does not load a neural network; the Make setup installs
the full optional stack for convenience. All models run locally on CPU.

```sh
.venv/bin/python rl/playtest.py --mode manual --episodes 1 \
  --goal "charisma>=10" --max-days 365
.venv/bin/python rl/train.py --goal "charisma>=10" --max-days 365 \
  --timesteps 100000 --gamma 0.999 --ent-coef 0.01 --progress \
  --reward-config rl/rewards.example.json --output rl/models/custom
.venv/bin/python rl/evaluate.py --model rl/models/custom \
  --goal "charisma>=10" --max-days 365 --episodes 20 \
  --reward-config rl/rewards.example.json --output rl/data/custom.json
```

Direct CLI counterparts include `--max-steps`, `--seed`, `--n-steps`,
`--batch-size`, `--checkpoint-interval`, `--resume`, `--stagnation-window`,
`--stochastic`, `--verbose` and `--quiet`. Each script's `--help` lists its
options. `--quiet` outputs only the JSON summary; it cannot be combined with
manual interaction. Failures still appear on stderr.

For dependency-free Rust inspection:

```sh
make rl-build
printf '%s\n' '{"op":"actions"}' '{"op":"observation"}' \
  '{"op":"step","action_id":0}' \
  | src-tauri/target/release/rl_env --dataset gtr2career --seed 42
```

The persistent JSON-lines protocol also accepts `{"op":"reset","seed":42}`.
It returns structured masks and `StepInfo`, including progress before/after
and reward components. Rust outcomes use PascalCase; the Gymnasium adapter
normalizes them to snake_case for Python reports.

## Known boundaries and proposed next improvements

The headless simulation is not identical to the live desktop/external game:
work/sponsor interactions are deterministic in this bridge; sickness and
unrelated randomness remain seeded. Event-result actions can choose submitted
results. The report warns when those occur. Do not interpret a championship
planning success as evidence that an external race will be won.

The current feed-forward policy does not observe every inventory identity,
quest/history detail or remaining action count directly; the action mask
conveys some, but not all, of this information. There is no automated
curriculum, exact fastest-path solver, guaranteed dead-end detector, or
automatic best-checkpoint selector. Checkpoints must be evaluated explicitly.
Reward tuning cannot repair missing state information or a simulator exploit.

The next substantial improvements, in order, would be externally validated
event outcomes (or a calibrated outcome model), richer **versioned** policy
observations with replay fixtures, a desktop route/diagnostics viewer, and
evaluation-driven checkpoint selection. These need separate design work;
they are not silently approximated by this workflow.

Run `make playtest-tests` for workflow/environment regressions. This work does
not alter savegame fields, save versions, or dataset revisions.
