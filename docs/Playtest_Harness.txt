# Prompt: Build an automated, tunable `playtest` tool for the RPG simulator

## Context

This is a Rust/Tauri application simulating a tabletop RPG. Core concepts:

- A **hero** with stats (charisma, stamina, money, etc.)
- **Objects** the hero can own (e.g. cars), some with requirements to buy/use
- A **market** where the hero buys objects
- **Events** the hero can take part in, each with randomized or user-entered outcomes (winning a trophy, gaining experience, getting a sponsor, an object breaking down, etc.)
- **Quests**, which are bundles of events
- Events and objects can have **requirements** (money, other objects, other stats) that gate what the hero can do
- Events happen on a **schedule** — a race or championship happens on a specific in-game date, not before or after

There is already a `playtest` program that plays the game automatically. The Tauri app exposes *some* API, but it's not confirmed to cover everything needed for full automated play — this needs to be investigated, not assumed.

## Overall goal

Turn `playtest` into a tool that:

1. Plays the game automatically, using a **pluggable strategy**, trying to reach a specific **goal state** in the **minimum number of in-game days**.
2. Stops a run when the hero reaches the goal, or "dies" (money or stamina go negative), or a configurable max-days/max-turns safety cap is hit.
3. Can run **in batches** (10s of runs while tuning, 1000s of runs for real experiments), collecting statistics.
4. Lets us **override tunable parameters** before a batch (event success probabilities, object prices, breakdown probabilities, etc.) so we can measure how sensitive difficulty is to each parameter.
5. Classifies difficulty from the distribution of "days to reach goal" across a batch, using **configurable thresholds** (e.g. today: ≤2 years = too easy, ≥15 years = hard, ≥20 years or never = near-impossible — but these thresholds must be easy to change later, not hardcoded logic).
6. Logs results to a file, with **configurable verbosity**.

This is an internal dev/balancing tool, not player-facing. Prioritize a clean, inspectable API over UI polish.

## Important constraints from how the game actually works

- **Scheduling matters**: some events (races, championships) can only be attempted on their specific in-game date. Playtest must know the calendar/schedule and only attempt those events when they're actually available — it can't just "run every event ASAP."
- **Requirements gate actions**: many objects/events require money, other owned objects, or stats above a threshold. The strategy layer needs to query what's currently *eligible*, not just what exists.
- **Some outcomes are randomized by the game engine** (dice/probability rolls — e.g. 50% chance to win, object breakdown chance).
- **Some outcomes are currently entered manually by a human** (e.g. the user types in "you came in 1st"). Playtest needs a way to control this input during automated runs — e.g. configure it to always answer "1st place," always "3rd place," or "random," per run or per event type.

## Note on time control

The game currently seems to advance in-game days on a **real-time timer** (e.g. +1 day per second, or faster/slower speed settings — seven days per second, etc.), presumably for normal play in the UI.

For playtest, this timer must be bypassable entirely:

- The headless engine interface (Phase 1) must expose a direct **"advance to next day" / "advance to next relevant date"** call that playtest invokes explicitly, with no real-world waiting involved. Playtest should be able to run through years of in-game time in milliseconds when it wants to.
- This doesn't mean removing the timer from the game — the UI/timer-driven mode can keep working as-is for normal play. It means the day-advance logic needs to be callable directly, decoupled from "a second of wall-clock time has passed," so both the timer (for normal play) and playtest (for batch runs) can trigger it.
- Flag this in the Phase 0 write-up if day-advancement is currently tied up with other timer-driven side effects (UI animations, autosaves, etc.) in a way that makes a clean "just advance the day" call non-trivial to extract.

## Note on watching a run live

Sometimes I'll want to **watch a single playtest run happen in real time** (e.g. to sanity-check a strategy or debug something visually), rather than always running at full speed. Playtest should support a configurable **pace**, separate from the trace-level logging in Phase 6:

- A `--speed` (or similar) option: `max` (default — no delay, for batch runs) vs. a real-time-ish mode where playtest paces itself (e.g. one day per N milliseconds/seconds, configurable) so a human can watch state changes happen, whether that's via the trace log streaming to a terminal or via the existing game UI updating live.
- If watching "live" implies driving the actual game UI (not just the headless engine) so I can see it visually rather than just reading log lines, flag this in Phase 0 — it may mean playtest needs an alternate mode where it drives the game through the normal Tauri-exposed commands (at a human-watchable pace) instead of the headless engine, and this should be a deliberate, explicit mode rather than something bolted on later.
- This is a "nice to have for debugging," not a core requirement — full-speed headless batch running remains the primary use case. Don't let it complicate the Phase 1-5 design; treat it as an additive mode.

## What to build

### Phase 0 — Investigate & propose a contract (do this before writing implementation code)

1. Explore the existing codebase (game engine crate(s), Tauri commands, event/quest/market/object data structures, RNG usage, and how the *current* `playtest` talks to the game, if it does).
2. Identify:
   - What state is already queryable (hero stats, inventory, calendar/current date, market listing, available/eligible events).
   - What actions are already callable as pure functions/API vs. only reachable through the UI or manual input.
   - Where RNG is used, and whether it's currently seedable/injectable or hardcoded (e.g., calls to `rand::thread_rng()` scattered around).
   - Where "manual user entry" outcomes happen in the code, and how that input currently reaches the engine.
3. Write up a short document (a few paragraphs + a list) proposing:
   - A **headless game engine interface** (ideally a Rust library API, not just Tauri IPC, so playtest can drive the game in-process without spinning up the UI) covering: get full state, list eligible actions/events for the current date, apply an action, advance time/day, check win/death condition.
   - How RNG will be made **injectable and seedable** (e.g. pass a `dyn RngSource` / seeded `StdRng` through the engine instead of ad hoc `thread_rng()` calls) without changing game balance/behavior.
   - How **manual-entry outcomes** will be intercepted and supplied programmatically (e.g. an `OutcomeProvider` trait with a `RandomOutcomeProvider`, `FixedOutcomeProvider(rank: usize)` etc., injected instead of reading stdin/UI input).
   - Any gaps: existing functionality that must be refactored to be reachable headlessly, and roughly how invasive that refactor is.
4. **Pause and confirm this contract with me before proceeding to implementation.** Flag anything where the "right" design isn't obvious (e.g. if actions have side effects that are hard to make deterministic, or if some game logic is tightly coupled to the Tauri/UI layer).

### Phase 1 — Headless engine interface

Implement the interface agreed in Phase 0:

- A way to construct a fresh game/hero state for a run (with a given RNG seed).
- A way to query, for the *current in-game date*: hero state, inventory, market state, and the list of currently eligible actions/events (already filtering by requirements and by schedule — i.e. don't expose actions that can't legally be taken right now).
- A way to apply a chosen action/event and get back the result (including whatever randomness or manual-entry outcome was used).
- A way to advance to the next relevant date/turn.
- A way to check: goal reached? dead (money < 0 or stamina < 0)? still going?
- Make sure this can run **without launching the Tauri UI**, e.g. as a lib crate + a small binary, so it's fast to run thousands of times.

### Phase 2 — Strategy system

Define a `Strategy` trait (or equivalent) that, given the current queryable state and the list of eligible actions, picks the next action to take. Implement at least these, so we can compare them later:

- **Random-eligible**: pick uniformly among currently eligible actions.
- **Greedy-toward-goal**: some simple heuristic scoring of eligible actions by estimated progress toward the goal state (define a reasonable heuristic, but make it easy to swap out / tune).
- **Do-nothing-but-required**: only take actions strictly necessary to hit scheduled quest events (baseline "laziest possible" run), useful as a lower bound.

Make it easy to add more strategies later without touching the batch runner. Strategy choice should be a CLI/config argument, not hardcoded.

### Phase 3 — Randomness & manual-entry control

- Every run takes an explicit **seed**, so a single run is fully reproducible.
- Provide an `OutcomeProvider` (or reuse whatever was designed in Phase 0) with at least:
  - `Random(seed)` — sample as the manual event normally would, but automatically instead of prompting a human.
  - `Fixed(rank)` — always report a specific outcome (e.g. always 1st place) for manual-entry events.
  - Configurable **per event or event-type**, since we may want, e.g., always-1st for one championship and random for another in the same run.

### Phase 4 — Parameter override system

- Add a way to override tunable game parameters **before a batch run**, without editing game source each time. E.g. a config file or CLI flags like:
  - `--override event.some_race.success_probability=0.7`
  - `--override object.some_car.price=15000`
  - `--override object.some_car.breakdown_probability=0.05`
- This should work by injecting overrides into the loaded game data/config at startup (not monkey-patching), so the same binary can run both "baseline" and "modified" batches.
- Document (in code comments or a small README) exactly which parameters are currently override-able, since this list will grow over time.

### Phase 5 — Batch runner & statistics

- CLI to run N simulations with a given strategy, outcome-provider config, and parameter overrides, using either a fixed list of seeds or auto-generated ones (log the seeds used, for reproducibility).
- For each run, record: outcome (goal reached / died — and if died, why: money or stamina / max-days cap hit), days elapsed, and (optionally, verbosity-dependent) a step-by-step trace of actions taken and outcomes rolled.
- After the batch, compute and print/log summary statistics:
  - Win rate, death rate (split by cause), timeout rate.
  - Distribution of "days to reach goal" among wins (min/max/mean/median/percentiles — e.g. p10/p50/p90).
  - Bucket the batch into a difficulty label using **configurable thresholds** (e.g. thresholds passed via config: `too_easy_below_days`, `hard_above_days`, `near_impossible_above_days`), so I can tune what "easy/hard" means without touching code.

### Phase 6 — Logging

- Log to a file (path configurable via CLI).
- Verbosity levels, at least:
  - `summary` — just the batch statistics.
  - `run` — one line per run (seed, outcome, days).
  - `trace` — full per-action trace per run (for debugging a specific weird run).
- Should be able to re-run a single seed at `trace` level to debug a specific bad/interesting run found in a `run`-level batch log.

## Deliverables

1. Phase 0 write-up (for my review before continuing).
2. Working headless engine interface + at least one binary that can complete a full run start-to-finish with a fixed seed and a trivial strategy.
3. Strategies from Phase 2.
4. Outcome provider / manual-entry control from Phase 3.
5. Parameter override mechanism from Phase 4, with a short list of what's currently supported.
6. Batch runner + stats + difficulty classification from Phase 5.
7. Logging from Phase 6.
8. A short README section (or update to existing README) explaining how to run: a single debug run, a small tuning batch (10s of runs), and a large experiment batch (1000s of runs) with parameter overrides.

## Non-goals

- No changes to the actual game UI or player-facing behavior.
- No need to make the override system generic/reflective beyond what's actually useful now — a hardcoded-but-documented list of override-able parameters is fine; don't over-engineer a fully dynamic config schema unless it's easy.
- Don't worry about performance beyond "1000 runs completes in reasonable time" — no need for parallelism unless it turns out to be slow, in which case flag it and we'll decide.

## Questions to resolve with me before or during Phase 0 (don't guess silently)

- Any case where making an action's outcome deterministic/replayable would require a nontrivial refactor — flag it rather than picking a workaround unilaterally.
- Any event/action whose "eligibility" logic is ambiguous or spread across UI code in a way that's hard to extract.
- Whether day-advancement and the real-time timer are cleanly separable, and whether a "watch it live" mode is worth building against the real UI vs. just a paced trace log (see time-control notes above).
- The exact goal-state condition (e.g. "all championships won" vs. a specific stat threshold) if it isn't already explicit in the code — confirm with me rather than assuming.
