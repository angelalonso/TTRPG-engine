NEXT DEVELOPMENT: DOMAIN-NEUTRAL ENGINE AND GUIDED DATASET AUTHORING
Investigation date: 2026-09-30

PURPOSE AND SCOPE
=================
This is an implementation backlog, not a claim that the proposed features
already exist. Implement one task at a time, including its acceptance checks.
The goals are:
  1. Keep game-specific vocabulary AND behavior in datasets/plugins.
  2. Make requirements, success modifiers, and consequences composable.
  3. Give dataset authors a guided editor that explains and tests those rules.

Investigated: src/, src-tauri/src/, gtr2career/*.csv, gtr2career/plugins/race_results.py,
dataset_editor.py, dataset_generic.py, the manifests, Makefile, CI, and relevant
existing documentation. Dataset HTML/assets were considered as linked content,
not as engine behavior. Do not inspect or modify dataset_tutorial/,
dataset_w_more/, or risiko_beim_schreiben/ while executing this backlog.
Do not use saved games or large playtest logs as authoritative specifications.

The racing plugin is currently in gtr2career/plugins/race_results.py.
gtr2career/. Treat it as game-specific content despite its present location.
The existing README calls the runtime domain-neutral; the source does not yet
support that claim. Changing labels alone will not achieve these goals.

EXECUTION RULES FOR THE IMPLEMENTING MODEL
=========================================
- Use the task IDs below. Dependencies are prerequisites, not suggestions.
  Execute in numerical order unless all dependencies of another task are done.
- Read the named symbols and their callers before editing; line numbers move.
- Preserve unrelated worktree changes. NEXT.md was already modified when this
  investigation began; it is not an implementation target.
- Do not rewrite lib.rs or App.tsx wholesale. Extract bounded shared helpers.
- Keep racing-specific CSV values, descriptions, identifiers, and images in the
  racing dataset. Do not rename Honda, races, or helmets just to make a scan clean.
- Add optional/versioned schema fields and migration support before replacing
  old fields. Do not silently reinterpret existing datasets or saved games.
- Use one engine implementation for desktop, headless, API, and author previews.
  Do not implement a second evaluator in Python or TypeScript.
- Requirements are gates; modifiers change numerical values; effects change
  state. Do not conflate "owns >= 3 objects" with "+5% success per object".
- Invalid configuration must produce actionable diagnostics, not zero values,
  false conditions, ignored effects, or successful-looking fallbacks.
- A game must work without age, budget, stamina, charisma, vehicle, license,
  work, sponsor, achievements, race tags, or any racing object IDs.
- Every behavior change needs an explicit fixture and test. Preserve intended
  racing behavior through dataset rules, not hidden compatibility branches.
- Mark a task done only after its acceptance criteria and relevant checks pass.
  Record any blocked prerequisite and actual command failure; do not invent
  successful tests. Do not bundle unrelated tasks into one large refactor.

CURRENT CAPABILITIES AND LIMITATIONS
===================================
These are source-backed capabilities, with important path differences.

C01. Player characteristics
  player.csv accepts id,name,value,min_value,max_value. Numeric characteristics
  are initialized dynamically; adjust_characteristic applies configured bounds.
  The dashboard lists most characteristics and draws bars for finite maxima.
  However money operations use "budget", event resource use/recovery uses
  "stamina", secondary rewards use "charisma", and age advances separately.
  run_status assumes negative budget/zero stamina mean terminal states.
  No configurable general characteristic-driven acquisition gate exists yet.

C02. Owned objects and acquisition
  Inventory is a Vec of individual OwnedObject instances, not stack quantities.
  Object IDs are currently generated with an inventory-length suffix; many
  checks infer definition identity using starts_with("<base_id>_").
  Buying checks affordability, requires_object_ids (ALL listed prerequisites),
  license_previous_id, and requirement_group substitutions. Licences use
  license_fee when positive and cannot be purchased twice.
  paddock_cred_bonus adds to charisma on acquisition.
  IDs beginning trophy_ and the exact IDs trophies, business_proposal, lower_cost
  cannot be bought. There is no general buyable/sellable/unique/reward-only flag.
  Frontend and playtest prerequisite checks do not fully reproduce group
  substitutions. The market blocks repeat purchases of lifetime_days=0 objects,
  while the backend generally permits repeats except licences.

C03. Selling, expiry, service, loans, rentals
  Sale value follows initial/annual/minimum resale fractions. Loaned objects and
  type=license objects cannot be sold. There is no backend trophy-sale ban;
  hiding achievements from the market does not prohibit inventory sales.
  lifetime_days/expiry and availability delays are supported.
  Fifteen cost/service slots are modeled and serviceable; daily automatic
  service interval processing only covers slots 1..4.
  Needed non-cosmetic services block use; a "cosmetic" substring in a cost ID
  makes that service nonblocking. Motorsport events can impose a charisma
  penalty for cosmetic damage and automatically mark tyre-named costs needed.
  Rental is one-event car rental: vehicle only, open-race name/track-day tags,
  price/25, licence, hardcoded race gear defaults, entry fee/stamina checks.
  Sponsor encounters can loan a vehicle until next year and grant longer-lived
  equipment. This is not a general loan/rent/use/consume object lifecycle.

C04. Event presentation and requirements
  events.csv uses day_of_year>0 for scheduled annual events and 0 for actions.
  Types/tags are strings; resolution_method names manual/random/encounter.
  Scheduled entry checks membership, day, funds, licence, selected object,
  availability/services, and, on desktop, stamina.
  required_object_ids is ANY listed selected object, not ALL and not a count.
  Motorsport demands vehicle. Open races/track days bypass selected-ID filtering.
  All scheduled entries still require an object argument; inventory-free
  events are not a complete supported path.
  Simulation eligible_event_entries restricts ALL events to vehicles and omits
  desktop stamina charging. Action execution/eligibility/encounter startup also
  differ between desktop perform_event and simulation apply_event.
  New action types are invisible in the fixed work/trade/sponsor activity tabs.
  No shared general event requirement language or rejection explanation API.

C05. Event outcomes and consequences
  Scheduled random results use a fixed success_rate; manual results accept
  success/successful/win/won/1/yes/true as success, other nonempty text as failure.
  Player-started non-encounter actions roll success_rate even when "manual".
  Actions can charge base_cost/stamina_cost, pay once, or activate recurring
  payouts/obligations. Successful desktop actions can launch linked encounters.
  Scheduled rewards target budget and charisma.
  Desktop event_outcomes.csv tests failure rows after an apparent success and
  uses their reward_pool_delta/charisma_reward_delta as outcome amounts.
  Desktop event_results.csv supports event ID and all-required-tag matching,
  sequential probabilistic row selection, reward amount and semicolon-separated
  characteristic:delta effects. A matching row turns success into failure.
  Candidate reported_result=="success" is the runtime selection test; the
  dataset's social_failure row has reported_result=failure and is therefore not
  selected there. Merely adding an effects string is not proof it runs.
  Simulation submission omits these two outcome tables, sponsor payments, and
  the desktop cost-rule completion path.
  position_rewards defines result choices/UI prize displays, but backend event
  payout remains reward_pool rather than selecting the position-specific prize.
  risk_factor is loaded but not used to calculate outcomes.
  No ordinary event rule can generally grant/consume N objects or compute
  success from the count of an object type.

C06. Cost rules and their condition language
  costs.csv defines money amounts. cost_rules.csv supports day_elapsed,
  event_completed, object_acquired; trigger_ref matches event/object ID or
  supplied event tags. An empty trigger_ref matches the trigger generally.
  Conditions for a rule are combined with ALL:
    event: id, outcome, tag
    action: id, outcome (legacy subject support)
    object: id, type
    player: inventory_count (TOTAL instances) or a characteristic ID
  Operators: equals/eq, not_equals/neq, contains, starts_with, greater_than,
  less_than. String matches normalize case; numeric parsing silently defaults
  to zero. There is no >=/<=, nested ANY/NOT, type-specific count, or history gate.
  player inventory_count only gates cost rules; it does not modify success.
  Monetary multipliers and probabilities are literal, not expressions.
  Immediate charges occur when affordable; otherwise costs remain pending.
  object_service creates a service requirement and ledger entry.
  Object-scoped daily rules run per owned object. Daily interval_days is a
  global-day modulo, NOT a general cooldown measured from last trigger.
  event_interval and no_event_days use race count/last_race_day, despite the
  generic column names. Explicit damage and automatic damage have distinct
  selection/probability handling. Do not assume probability is rolled once.
  Action cost contexts currently omit event tags.

C07. Recurring obligations
  obligations.csv pays any named resource on configured intervals/weekdays,
  counts payments/faults, optionally blocks payouts, and can end an event or
  kill the player. It has required_event_type and max_active fields.
  ActiveEvent holds counters shared by its obligations, not per-obligation
  counters. Multiple rows for one event can therefore interfere.
  Some start checks use only the first obligation row.
  Additional job exclusivity depends on type=work and exact act_work/act_work_b
  IDs. Sickness, recovery, salary blocking, and completion charisma are
  hardcoded core behavior. Month/year intervals currently mean 30/365 days.

C08. Quests, standings, achievements
  events reference quest_id; quests can require a licence, charge a join fee,
  and require a previous-level trophy. Joining adds event alarms, not actual
  event participation. There is no explicit generic mandatory/optional entry
  or automatic-participation policy.
  Only type=championship quests are rendered on the quest screen.
  Standings are calculated in both App.tsx and the racing Python plugin using
  max(1, number_of_rounds-position+1) within prize positions.
  quests.success_points/failure_points are loaded but not the scoring basis
  of that UI/plugin calculation. championship_rewards is displayed, not paid
  by the backend quest-finalization path.
  Trophy awards are based on top-three position in the last/finale event,
  not final cumulative standings or completion of every required event.
  The first achievements catalog object becomes the generated trophy template.
  There is no persistent generic quest-run status/finalization/reward receipt;
  repeated years and missed/out-of-order rounds are not robustly represented.

C09. Encounters
  Actions support attribute thresholds, required object presence, resource
  costs, cooldowns, success/failure attribute deltas, target actor, and text.
  Success = clamp(base_success_rate + attribute*scale + object bonuses, 0, 1).
  Object bonus is added once per matching encounter_objects ROW with ownership,
  not once per owned instance. Count-based scaling is absent.
  Opponents support random/aggressive/defensive runtime selection; max turns,
  loss-condition attributes, turn order, retreat, and tiebreakers exist.
  attack_defense is an optional encounter mode.
  action_weights, scripted_actions, ai_weight, rng_mode, and
  consumable_in_encounter are loaded without corresponding runtime execution.
  consumes_object removes an exact required ID from a temporary inventory;
  owned IDs have suffixes, and the modified vector is not synchronized back
  to GameState inventory. Do not advertise reliable consumption.
  Implemented final consequences: grant_object, attribute_delta, custom_event.
  custom_event is actually sponsor-only activation, not a generic event hook.
  Intermediate encounter attributes are not generally copied back to player
  characteristics; final outcome deltas are a separate mechanism.
  Grant paths do not uniformly initialize lifetime/availability/acquisition
  hooks. Unsupported consequence types are silently ignored.

C10. Plugins
  Race-tagged submissions call a fixed Python race-results plugin.
  TTRPG_RACE_RESULTS_PLUGIN/TTRPG_PYTHON override executable selection; default
  paths are gtr2career/plugins/race_results.py with a repository-relative fallback.
  Protocol: JSON stdin/stdout, event, prior results, position, competitors,
  damage choices and standings; an interactive Tkinter mode also exists.
  ResultPromptModal automatically opens that external UI and offers retry or
  in-game override, but backend race submission still invokes the plugin.
  There is no dataset plugin manifest, generic dispatch/result schema, timeout,
  protocol version, explicit capability discovery, or clean optional-plugin
  contract. Interactive invocation waits while the game mutex is held.
  Noninteractive Python cannot be presumed available on every target.

C11. Editor and validation
  The visual editor already shares colors.csv token names with the game and
  supports objects, events, quests, costs/conditions, and inventory labels.
  It is a mockup, not an engine-backed preview: budget/day are hardcoded;
  inventory/dealer frames are constructed but not packed as working pages.
  Basic event/quest screens only add rows, with limited fields and racing-only
  readonly tag/type lists. They do not guide requirements or consequences.
  Object editing reconstructs rows and loses fields it does not expose.
  Visual quest export drops championship_rewards, driver_names, and level.
  Raw-table editing saves directly to disk; visual lists remain stale and
  later export can overwrite those edits. Export projects onto fixed headers.
  Generic SECTIONS omits event_outcomes, event_results, texts, all encounter
  files, and plugins; its claims of "every engine table" are not true.
  condition rows use rule_id, but raw editing requires id, blocking saves.
  Guidance/defaults contain racing assumptions and inaccurate statements
  (e.g. licence_fee handling, interval/race semantics, resolution behavior).
  Validator checks some references/duplicates/probabilities, but not all
  tables/operators/units/effects/encounter relationships. Parse failures become
  warnings with skipped rows, and missing files can produce empty catalogs.

PROPOSED TARGET CONTRACT
========================
Task T07 must make the following design precise before implementation. This
is a recommended bounded design, not an existing repository schema.

Keep CSV authoring. Use optional version-2 tables for:
  condition_groups.csv: id,mode (all/any/not)
  conditions.csv: id,group_id,subject,selector,field,operator,value
    subject=group references another group through selector; validate cycles.
  requirement_bindings.csv:
    id,target_kind,target_id,operation,group_id,message
  numeric_modifiers.csv:
    id,target_kind,target_id,parameter,operation,expression,group_id,priority
  effects.csv:
    id,effect_group_id,order,operation,target,selector,expression,options
  effect_bindings.csv:
    id,source_kind,source_id,trigger,result,group_id,effect_group_id,
    probability,repeat_policy
These headers are a starting contract; T07 must settle selector/options syntax
and all enums once, document them, and make metadata reflect that same contract.
Do not let subsequent tasks independently invent incompatible columns.

Use a small parsed numerical expression language, NOT Python/JS/Rust eval:
  literals, characteristic("id"), inventory_count("id|type|tag|group","value"),
  context("declared_numeric_field"), arithmetic, min/max/clamp.
Typed condition subjects also cover inventory, event history, quest state,
active events, calendar, selected-object state, and explicitly supported
plugin result facts. Counts refer to definition IDs, never string prefixes.
Ownership/usable/loaned filters must be explicit and explainable.

Example target behavior:
  clamp(0.30 + 0.05 * inventory_count("type","ingredient"), 0, 0.90)
With no ingredients success is 0.30; with three usable matching instances it
is 0.45; with twenty it is capped at 0.90. A UI test must display those exact
values. This is an example generic event, not a racing core special case.

Generic semantic models:
  object definition + unique owned instance; acquisition/transaction policies;
  typed conditions; effective numeric parameters; ordered effects;
  event attempt/result; active event/obligation; quest run/progress/standings;
  reward receipt; dataset-selected optional plugin.
The racing game retains race/vehicle/licence/sponsor/championship terminology
as its own labels, categories, requirements, formulas, and plugin.

Compatibility:
  Version-1 CSVs remain readable through explicit adapters and warnings.
  New neutral names become canonical. Old serialized keys remain aliases or
  migrate through a save-version adapter. Do not guess version from game type.
  Version-2 configuration is authoritative; legacy and new rules must never
  both charge or reward the same action.
  Do not remove legacy racing behavior until T35 migrates and verifies it.
  Compatibility code must be isolated and scheduled for eventual removal,
  not spread across the new generic evaluator.
